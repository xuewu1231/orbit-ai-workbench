过去两年里，几乎所有研发团队都经历过同样的困惑：为什么同一个旗舰大模型，在别人手里能一气呵成跑通复杂模块，在自己团队手里却总是改东坏西、上下文越聊越糊涂？

核心差距早已不在“会不会写提示词（Prompt）”，而在于你为模型搭建的 **Harness（运行骨架与护栏系统）**。

## 一、四代演进：从“雕花提示词”到“看 Skill 调 CLI”

回顾 AI 辅助研发与自动化的演进，可以清晰地看到四个代际跃迁：

1. **1.0 角色提示词时代**：在对话框里塞满“你是一位拥有 20 年经验的架构师……”，模型只能纸上谈兵，无法触碰真实文件系统与终端。
2. **2.0 死板流程图（DAG Workflow）时代**：人类用连线节点把步骤写死。看似可控，一旦真实环境报出一个未预设的异常，整条流水线瞬间卡死。
3. **3.0 重型工具全量挂载时代**：一口气给 Agent 塞进十几个外部服务与上百个工具定义，结果任务还没开始，30% 的上下文窗口已经被工具说明书占满，注意力严重稀释。
4. **4.0 推理模型 + 极简基座 + 按需 Skill 时代**：只给 Agent 保留最原子的基础能力（读写文件、搜索代码、执行终端命令），把领域专长封装成按需读取的 `SKILL.md` 与轻量 CLI。

## 二、给全局规则做减法：为什么越写全大写警告越无效？

很多团队的根目录规则文件越攒越厚，动辄上千行，写满了 `CRITICAL: NEVER DO X`。实测表明，当全局常驻规则超过 150 行后，每多加一条低频禁令，模型对核心架构约束的遵循度就会下降一截。

我们的内部原则非常干脆：**全局规则只写“每次会话 100% 必用的项目地图与构建命令”，把所有特定场景规范全部下沉到独立的 Skill 目录中**，需要改 UI 时才加载设计 Skill，需要发版时才加载发布 Skill。

## 三、用「阻断式自检钩子」替代人工肉眼盯屏

真正让团队敢把两小时级别的任务放手交给 Agent 的关键，是在 Harness 层引入**硬性闭环验证（Deterministic Verification Gate）**：

- **权限分层隔离**：本地沙箱默认放开工作区读写与测试执行，同时在配置层硬性封锁密钥文件（`.env`、私钥目录）与高危远端推送指令。
- **退出码自修复闭环**：在任务结束钩子中挂载增量类型检查与核心单测脚本；一旦返回非零退出码，直接把标准错误流回传给 Agent 触发自动修复，直到绿灯通过才允许唤醒人类审查。

## 四、团队商业级 Skill 的封装与分发实践

把内部跑通的 Skill 升级为可跨项目复用甚至商业化交付的资产时，核心差距在于三件事：

1. **自带确定性辅助脚本（Scripts）**：不要让模型每次现场手写解析逻辑，把易错的数据转换、去底压缩、AST 扫描写成确定性脚本放在 `scripts/` 目录供它直接调用。
2. **正反例参考锚点（References）**：提供 1 个满分输出样本与 3 个典型反面教材，比写五千字抽象形容词管用十倍。
3. **一键 CLI 版本同步**：通过轻量命令行工具支持团队成员或订阅用户一键拉取最新规范更新，把静态文档变成持续进化的活服务。
