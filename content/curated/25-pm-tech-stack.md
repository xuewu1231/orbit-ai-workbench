作者把问题收成四个：看清从硬件到 Agent 的全貌，分清哪些知识会改变产品决定，用真实案例看优秀的人怎么拍板，再按目标岗位决定去哪学、练什么、怎么验收。

## 一次请求，其实穿过五层

一次 AI 请求从底层算力、数据、模型，走到推理服务，再到用户碰到的应用。产品经理要能指出问题落在哪一层，以及那一层怎么影响效果、速度和成本。

硬件与算力决定能不能部署、能撑多大、运行有多贵。应用产品经理知道算力、显存、部署方式和成本的关系就够用，比如私有化一个模型和走云端 API 为什么不是同一笔账。做算力平台的人，才需要钻进规格和调度。

数据与训练决定能力怎么来。产品上更常要拍的是：这件事要不要训练。企业内部知识，用检索把资料在调用时送进去，还是用微调去改参数，解决的不是同一个问题，也可以一起用。

模型层是能力和边界。选哪一类：文本、多模态、偏推理、还是用来检索的向量。上下文更长，不保证长文效果更好。排行榜接近的模型，擅长的任务可以差很远，所以要按自己的场景做测试。

推理与服务把模型变成能调用的 API：延迟、并发、计量、故障时的降级。同一个模型有多家供应商时，怎么选、请求分给谁，是这一层的产品问题。

应用与智能体是用户直接碰到的。问答、固定路径的工作流、会自己调工具的 Agent，不是同一档自主程度。规则清楚的分类，工作流就够。要跨系统查询再执行，才更像 Agent 的活。

## 值不值得学，看它改不改决定

作者从这五层收出六类日常会用到的知识：模型能力与边界，数据与上下文，应用与编排，推理服务与成本，效果评测，安全与可靠性。

其中评测他写得最硬：一个能跑的 Demo，离业务要求还远。回答准不准，任务稳不稳，改完有没有真变好，都要对着真实场景看。

岗位不同，往下钻的深度不同。应用、知识库、Agent、模型服务、基础设施，各自先碰会改决定的那几项。工具会换，机制、适用场景和约束更值得留下。Dify、LangChain 这类适合拿来把检索或 Agent 做一遍，不适合当成长期的知识本身。

## 一个他们没做的功能

作者负责过 Token 网关，讨论过智能路由。一种是按任务难度换模型：简单的给便宜模型，难的给大模型。难处是系统怎么判断难。很短的数学题可能很难，很长的文章可能只是抽取。再加一个分类模型，就多出延迟和成本；分错了，还要重跑。所以不能只比单次价格，要看质量达标之后的总账。

另一种是同一模型的多家供应商之间调度。价格和延迟若比较稳，可以先用手动的优先级。要按实时错误率来回切，就得有监控、判断和切换，维护成本一起上去。

他们当时没做复杂的自动路由，做了可以多层手动配置的基础路由。更急的是两件事：不同供应商、不同模型类型的接入，以及从客户请求到返回的整条链路稳不稳。动态路由能省下多少、体验提升多少，当时没有足够依据。以后数据齐了、规模上来了，再重新估。

他用这次拍板说明：懂技术，是能说出实现条件和代价，再按产品所处的阶段决定先做哪件。

## 学完，用一次带对比的实践来验收

先定岗位，再选要钻的知识和一个小项目。项目不必大，但要有同一条件下的比较：效果、速度、成本，以及为什么最后选这个。能跑只说明初步可行。有数据、有对比、有取舍，才算产品判断。
