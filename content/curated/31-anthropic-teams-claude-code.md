Anthropic 在 2025 年 7 月坐下来问了自己公司里的人：你们平时到底拿 Claude Code 干什么。原文是一篇官方介绍，语气偏整齐。下面不跟着它的句子走，按他们讲到的事，用能看懂的话重说一遍。

数字都是他们自己说的。我们没有再测一遍。

他们自己的结论可以收成一句：这东西不只是让程序员写得更快。会把问题讲清楚的人，开始能把解决方案做出来。用得好的队，把它当一起想的同事，不是一台只负责吐代码的机器。

先看他们聊到的六件事。后面每一章展开一件，最后把能拿走的划出来。

1. 进一个陌生仓库，先问该看哪几个文件。
2. 测试和审阅这些烦事，写完别再丢掉。
3. 线上出事，把报错、文档、截图一起给它。
4. 做新功能时，不一定要先会那门语言。
5. 散在各处的说明，收成下次还能用的几页。
6. 市场和法务这样的部门，做出了自己的小工具。

## 进一个陌生仓库，先问该看哪

新人上手，最耗时间的往往不是写代码，是搞清这堆文件谁依赖谁。

数据基建团队的新数据科学家，会把整个代码库交给它。仓库里有人写过 `CLAUDE.md`，它会先读这些说明，挑出和眼前问题有关的几份，讲这条数据管道依赖谁、看板上的数是从哪几个上游来的。他们说，这代替了以前单独做的数据目录。

产品工程把它叫做任何编程任务的第一站。修一个 bug、做一个功能、做一次分析，先问：我该打开哪几个文件。省掉的是动手之前自己到处翻上下文。

> 重点：先让它指出该看的文件，再让它改。仓库里的 `CLAUDE.md` 写得越具体，这一步越不像碰运气。

## 测试和审阅，写完别再丢掉

写测试、看代码，两件都重要，也都烦。他们用得最多的，就是这两件。

产品设计团队让它给新功能写比较全的测试。拉取请求上的评论走 GitHub Actions：格式问题、测试用例要不要重写，由它在评论里处理。人不用再为这些来回改。

安全工程团队改的是自己的老习惯。以前的顺序是：写设计文档，糊一版能跑的代码，再重构，最后测试干脆不做了。现在先让它给一版伪代码，再按测试驱动往下写，人隔一会儿回来看一次。他们说，这样交上去的代码更经得起测。

:::diagram-test-before-after:::

推理团队还有一种用法：要把测试写到自己不熟的语言里，比如 Rust。人讲清想测什么，它用这个仓库本来的语言把逻辑写出来。测的是行为，不是人先把语法学完。

> 重点：测试要在写的过程里就在，不要留到「有空再补」。审阅里那些重复的格式和用例整理，可以交给流水线，人看剩下的。

## 线上出事，把线索一起给它

故障里最怕的是：代码不熟，时间又紧，人在脑子里硬推。他们的做法是把堆栈、文档、系统当时的表现一起给它，让它顺着调用把路走一遍。

安全工程在事故里就是这么干的。以前靠人肉扫代码，一个问题常常要 10 到 15 分钟。他们说，现在大约快了三倍。

产品工程因此敢去碰别的组的代码。问法很具体：「这个 bug 你能修吗？我看到的现象是这样。」它给出改法，人再看这版改得对不对。不必先把另一个工程组叫过来。

数据基建有一次更具体。Kubernetes 集群突然不再调度 Pod。他们把监控面板的截图给它，它带着人在 Google Cloud 的界面里一个菜单一个菜单地点，直到发现是 Pod 的 IP 地址用完了。然后它给出新建一个地址池、再挂回集群的命令。他们说，故障当中少花了大约 20 分钟。

:::diagram-ip-exhaustion:::

> 重点：别只丢一句「帮我看看」。把你看见的现象、报错、截图一起给。那次有用，是因为它在控制台里带着人走，不是猜了一个原因就停。

## 做新功能，不一定先会那门语言

以前做一个功能，默认要懂那门技术，还要留出整段时间。他们现在用它把想法先跑起来，会不会写这门语言不再是门槛。

产品设计会把 Figma 的设计稿交给它，然后让它自己转：写代码，跑测试，不行再改。人给的是一个还比较抽象的问题，过一段时间回来看结果，再收尾。有一次，他们让它给自己加上 Vim 快捷键，人几乎没怎么盯。

同一个团队还有个事先没想到的用法：在设计阶段就把错误状态、逻辑分支、系统会处于哪些状态画出来，边角情况在画的时候就露出来，而不是等写到一半才发现。他们说，这样后面能少排掉好几个小时。

数据科学家里有人 TypeScript 并不熟，照样用它做整页的 React 应用，用来看强化学习模型跑得怎么样。在一个沙箱里，一句提示就写出整页可视化。任务简单的时候，第一句不够就改一句再试。他们并不需要自己看懂生成出来的代码。

这里要留一句他们自己的限定：这么做，是因为这件事本身简单。复杂的、要上线的，他们仍然回来看过再收。

> 重点：简单的可视化、自己用的原型，可以让不会那门语言的人做完。设计阶段先把错误状态画出来，比等代码写出来再补洞省时间。

## 散落的说明，收成下次还能用的几页

文档通常散在 wiki、代码注释和某个人脑子里。他们用 MCP 和仓库里的 `CLAUDE.md`，把这些收成谁都能打开的说明。

推理团队里不做机器学习的人，靠它解释某个只跟这个模型有关的函数。以前要搜将近一小时，他们说现在大概 10 到 20 分钟，少了大约八成。

安全工程让它读进好几处文档，写成 markdown 的处理手册和排障说明。这些短的文件，接着就会变成下一次查故障时的上下文。他们觉得，这比每次去翻整本知识库快。

> 重点：说明要写在下次还能喂给它的地方。一次排障写成一页手册，下一次就不用从头搜。

## 市场和法务，做出了自己的小工具

增长市场做了一条自己的流程。一张表里有几百条广告，它找出效果差的，在字数限制里写出新版本。他们用了两个分工不同的子代理，几百条新广告从要花几小时，变成几分钟。

他们还做了一个 Figma 插件：认出画框，把标题和描述换掉，一批最多大约 100 条。以前人在里面复制粘贴要几个小时，现在每一批大约半秒。

法务做的东西更不像「开发任务」。他们做了一个电话树的原型，让同事找到该找的那一位律师。一个部门要的内部工具，不必先等一个专门的开发组排期。

> 重点：小工具值得做的标志，是这件事现在靠人重复做，而且规则说得清。字数限制、哪条广告效果差、该找哪位律师，都属于这种。

## 划重点

六件事放在一起，真正能拿走的是这几条。

1. **先讲你看见的现象，再让它改。** 产品工程的问法就是「我看到的是这样，你能修吗」，然后人看它提出的改法。
2. **测试和说明留在仓库里。** 安全团队把「写完就放弃测试」改成先要伪代码、再按测试往下做。这和站上另一篇 [Claude Code 团队怎么验收](/read/claude-code-verification) 是同一件事：没有能再跑一遍的证据，人就得自己看每一处。
3. **出事时把截图、报错、文档一起给。** 数据基建那次，它是一屏一屏点进 Google Cloud，才找到 IP 用完了，并给出命令。
4. **简单的图、广告变体、内部小工具，可以让不会那门语言的人做。** 难的、要交给别人用的，他们自己也是看过再收。官方写得很清楚：任务简单，第一句不够就改一句再试。
5. **用得好的队，把它当一起想的人。** 他们的原话落在这里：探索可以怎么做，先做一版看看，技术和不写代码的人把发现互相传开。代码只是其中一件事。

原文在文末。想看他们后来把验收做成什么样，从上面那篇验收笔记接着读。
