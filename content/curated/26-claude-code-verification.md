这篇是 Addy Osmani 2026 年 11 月 17 日发在 X 上的长文，讲 Claude Code 团队自己怎么验收。下面是我们留下来能对照的笔记，不是原文。

他先把规模说清楚：团队里绝大部分代码由 Claude 写，也由 Claude 审。他自己写的比例大约是九成。没有验收时，人得自己看每一处，所以同时只能开一两个。有了验收，才能把更多个放在一起跑。

他举过一次内部测试：生成结构化文件时，另用一个评分者按量表检查，任务成功率比普通的提示循环最多高出约 10 个点，难的题提高更多。测试、基准、规格一旦写成软件，就可以反复跑，不必每次都再花很多 token。某类失败反复出现，就收成钩子，或写进 `CLAUDE.md`，让下一轮少犯。

## 三种值得先做的测试

测试不稳，代理会学会再跑一遍，而不是改代码。测试太慢，一轮里能跑的次数就少，问题更难定位。重的测试放在提交之前。

端到端放在第一位。它描述的是真人会走的路径，比如把东西放进购物车、结账、看到确认页。整条路径通了才算通，不容易被局部的绿灯骗过。他建议给代理手和眼睛：网页用浏览器，手机用模拟器，后端把服务在本地跑起来。功能图按用户视角列路径、快捷键、选择器和预期结果，既是说明书，也是评分表。单元测试更快，但单元全绿，功能仍可能是坏的。

属性测试看的是「这句话不该被打破」。先写一条你认为永远成立的话，再用库去造大量输入来反驳它。JavaScript 他点了 fast-check，Python 是 Hypothesis，Rust 是 proptest。常见的四类：编进去再解出来必须还原；余额不能变成负数这样的不变量；同一件事做两次和做一次结果相同；优化后的实现要和笨但正确的实现一致。规格已经和线上行为对不上时，这种测试比对着过期文档更有用。

差异测试用在迁移。新旧系统喂同一批输入，结果不一样就有问题。输入用随机生成的，或从线上流量里抽样。空白这类无关差异先抹平，允许不同的地方单独列一张已批准的清单。

## 验收怎么放进日常

验证的意思是把这次改动跑起来。他让仓库里放一个叫 verify 的技能，放在 `.claude/skills/`，尽量靠近相关代码。里面写清怎么启动、怎么点、怎么看结果。提交前先用它。技能本身要快、要稳，值得单独打磨。

失败用来决定要不要叫人。Claude 先跑检查，失败了自己修。同一项修了三轮还是失败，就停，把人叫来。

检查由这块代码的主人来写，写到它标出的问题和主人会标的是同一类。把人叫来时要写明原因，不要让人从 diff 里重新猜。

他们有一张 39 条的可靠性清单。每条有一个能从 diff 里读出来的触发条件、一条检查，以及它背后的事故或拉取请求。例如会话恢复会读到旧记录：存储或消息类型变了，就要问新字段在旧记录上会不会安全读入。Claude 只查触发条件对得上的几条，通常是 3 到 10 条，不必把过去的事故全背下来。

审阅不靠加人。再叠一个更贵的审阅者，往往不如把第一个调好。每个代码区域有一份 `REVIEW.md`，写这一块该看什么。后面几轮接着前面的上下文和已经失败过的地方看，不从零再查一遍。

改动不能改裁判自己。代码评审读的是基线分支上的 `REVIEW.md`，不读这次拉取请求里改过的那份。评审对着某一次提交，提交还在往前推，评审结果就作废。便宜的检查先跑。测试、构建、检查器在开拉取请求之前就该过。

每次提交盖一个章，写明这次是怎么验证的。没验证也要盖上「没有」，以后查得到。另有一道门，可以挡下这次会话里没走过代码评审或 verify 的提交。门有三档：关掉、只记录、真的拦住。只记录的时候先看会不会误伤。拦住两次之后，下一次放行，避免 Claude 卡死。被拦住的提交可以在说明里写为什么没验证。

## 检查本身也要被检查

他们看三件事：合并后又撤回了多少，维护者在合并前拒绝了多少，以及一批体量相近、后来一直干净的改动。正式评估会把仓库恢复到当时评审的状态，每题只给一句「毛病是什么」。只有说中这句的发现才得分。已经合并且后来稳定的改动拿来当对照，防止到处报警。

召回率拆开看：原始发现、验证之后、最终评审。合在一个总分里，会看不见系统把已经找到的问题弄丢了。发现还会标重要、细枝末节、或者本来就在。本来就在的，不记在这次作者头上。

漏掉的问题要变成规则，有两条路。一条是从人的评审意见和撤回里找重复：至少出现在两个拉取请求里，而且能从 diff 看出来。三个代理先试着反驳这条规则，人再在拉取请求里批准。另一条是拿和已知事故有关的拉取请求，让三个找错的代理重放。至少两个找到，才算查得出来。小 diff 上还是漏了，就值得写进 `REVIEW.md`。

不稳定的测试不能靠跳过、加等待或重试到通过。找不到原因，就删掉，并写明为什么删。规则、测试和说明文件只会变多，他们按周期删掉不再值得跑的。

他收在一处：验收层要像别的系统一样维护。裁判不能被它要裁判的改动改掉。用真正出过的问题给它打分。漏了就写下来，写下来的也要修剪。人的工作从读每一处 diff，变成规定什么叫做完，再看证据。
