在 Claude Code 团队，我们绝大多数的代码（**约 90%**）都是由 Claude 编写并由 Claude 审查的。在这样的规模下，我们如何装备我们的 Agent、让它们能够**拿出真实证据来验证自己的工作**，就变得极其关键。

验证闭环（Verification loops）是让你能够把更多工作放手交给 Claude 的基石。没有验证闭环，你同时最多只能开一两个 Claude，因为每一样东西你都得自己亲眼检查。有了验证闭环，你可以同时并行运行几十甚至上百个 Claude。

这是因为，给 Agent 提供验证自身输出的手段，是提升质量极有效的方法。在我们围绕结构化文件生成的内部测试中，引入一个独立的评分器（grader）对照评分量表（rubric）检查 Claude 的产出，相比标准的提示词循环，任务成功率最高提升了 **10 个百分点**——而且题目越难，提升幅度越大。

过去验证起来非常昂贵的东西（测试、基准压测、规范文档、真实的端到端运行），如今向 Agent 索要起来成本极低。就像写业务代码一样，Agent 可以迅速生成测试、基准和规范。而且一旦生成出来，这些测试与基准是作为普通软件运行的，因此可以高频反复执行，而几乎不消耗多少额外的 Token。

你还可以利用验证结果反过来提升 Agent 在该任务上的表现，把验证闭环彻底跑通。例如，如果 Agent 反复在某项「检查日志是否泄露用户数据」的测试上挂掉，你就可以创建一个 Hook，或者在 `CLAUDE.md` 里写一条更明确的规则来避免后续再犯。这（在绝大多数情况下）能阻止同类问题再次发生。

既然验证对于高速产出高质量代码如此关键，你究竟应该采用哪几类测试？又该如何把它们部署到你的研发流水线中？这篇文章将回答这些问题，并分享 Claude Code 团队内部正在使用的完整验证流程。

## 并非所有测试都生而平等：最值得投入的 3 类测试

无论你选择哪种测试类型，都有几种常见的失败模式必须避开。

如果你的测试是**偶发抖动的（flaky）**，你就会把 Agent 训练成「失败了就重跑一遍试试运气」，而不是去修复真正出错的代码。如果你的测试**太慢**，Agent 在每一批次之间跑测试的频次就会变少，导致很难精准定位问题出在哪里。更重的测试最好放在你准备提交（commit）改动之前再统一运行。

下面是我认为最值得投入精力的三类测试。

### 1. 端到端测试（E2E tests）

如果你只能集中精力做好一类测试，那就选**端到端测试**。这类测试描述的是真实的用户完整流程，比如把商品加入购物车、结账付款、一直跳转到订单确认页。

端到端测试之所以如此有效，是因为它**极难被糊弄过去**——要么整条功能链路真的跑通了，要么就是没跑通。它拥有毫无歧义的「完成标准（done criteria）」，而且能具体指明到底是哪里坏了。

![单元测试也许只会报一句「Error: Timeout after 30 seconds」，但端到端测试能直接截出故障现场画面并给出清晰的问题描述。](/figures/claude-code-verification/img_02.jpg)

虽然单元测试速度更快、也不容易偶发抖动，但很容易出现「单元测试全绿，实际功能却坏了」的情况。这是因为 Agent 和单元测试本身都没有理解完整的用户任务。

在端到端测试中，给你的 Agent 配上接触真实运行中系统的「双手和眼睛」非常管用。你可以编写一个 Skill，利用 Chrome DevTools 协议（CDP）、模拟器或 API 测试底座来启动、操控并检查应用。

**功能地图（Feature map）**可以充当 Agent 的向导和评分量表——它通常会站在用户视角列出所有功能，写明访问路径、键盘快捷键、DOM 选择器以及预期结果。

### 2. 属性测试（Property tests）：绝对不能被打破的约束

很多传统测试写的是「你预先想到可能会出错的地方」。而属性测试专门盯的是**人类往往会漏掉的边界情况**——而那恰恰也是 Agent 最常翻车的地方。

做法是：你先写下一条你认为绝对不应该失败的断言，然后用属性测试库（JS/TS 用 `fast-check`，Python 用 `Hypothesis`，Rust 用 `proptest` 等）自动生成成千上万组随机输入，千方百计试图证伪它。

几乎每一个软件项目里都天然存在大量这样的属性（Properties），例如：

- **往返编解码（Round-trip encoding）**：「如果你把 `X` 编码后再解码回来，得到的依然是 `X`。」这同样适用于解析（parsing）和序列化（serialization）。
- **不变量（Invariants）**：永远必须为真的条件，比如「账户余额永远不能变成负数」。
- **幂等性（Idempotency）**：同一个动作（数据迁移、归一化、重试）执行两次的效果，与执行一次完全相同。
- **等价性（Equivalence）**：经过复杂性能优化的代码，产出的结果与朴素但绝对正确的基准实现完全一致。

属性测试库是让 Agent 保持诚实的绝佳利器，因为它生成的边界用例不会带有编写原代码的那个 Agent 同样的思维盲区。当规范文档已经偏离线上真实行为、不再适合作为可靠验收依据时，它在代码重构与重写场景下尤其管用。

### 3. 差分测试（Differential tests）：把旧系统当成标准答案（Oracle）

差分测试在要求功能行为保持不变的**大规模迁移场景**下格外有效。在这类测试中，你把相同的输入同时喂给旧系统和新系统运行，对比两边的输出是否一致。一旦结果不同，就说明存在 Bug 或破坏性变更需要修复。

做好差分测试的关键，是使用随机生成的输入或线上真实流量的采样。同时，你还需要把空白字符等无关差异做归一化处理，并针对「新环境理应与旧环境不同」的已知情况维护一份已批准变更白名单。

## Claude Code 团队是如何思考验证的

我们此前写文章介绍过 Anthropic 内部是如何做代码审查（Code Review）的，而这篇文章打算更深入地拆解我们如何**验证（verify）**自己的工作。

### 验证意味着真正把改动跑起来

把应用端到端跑起来，比单纯跑测试脚本更重要。你不会在没用模拟器点开试过的情况下就发一个 iOS 改动，对 Claude 来说也是一样。

Claude 完全可以像人类工程师或 QA 测试工程师那样测试整个应用：改网页前端时让它调用 Claude Chrome 扩展，改移动端时接 iOS 或 Android MCP，改桌面端时用 Computer Use，改后端时直接在本地把服务拉起来测。

为了把「怎么启动模拟器或运行应用」固化下来，请在仓库的 `.claude/skills/` 目录下创建一个名为 `verify` 的 Skill——离相关代码越近越好，需要多少个都可以加。Claude 知道在提交改动前主动调用 `verify` Skill。

接下来，花精力把你的 `verify` Skill 打磨得又快又稳。让 Claude 反复迭代它、对它做压力测试。它是你的冒烟测试底座（smoke test harness），必须坚如磐石。

当你给 Claude 提供了端到端冒烟测试自身改动的方法，产出质量会有质的飞跃。你会看到它像人类开发者一样快速迭代并抓出真正的错误。在 Anthropic，我们几乎所有的改动都是这样测试的。

### 只有挂掉的测试才需要人类介入

没有人读得完每一笔改动，所以我们把「检查失败」作为决定什么事情需要人介入的筛选器之一。Claude 会自己跑检查并尝试修复所有报错；**如果某项检查连续修了三轮仍然失败，Claude 就会停下来，请人类介入。**

### 代码负责人自己写检查规则

谁负责这块代码，谁就亲自为它编写检查规则，并不断打磨，直到这些规则能精准标出负责人自己审代码时会标出的问题。当某条检查把人类审查者拉进来时，它必须写清楚**为什么**拉人，省得审查者还要自己从一堆 diff 里猜原因。

### 可靠性检查按 Diff 按需触发

我们维护着一份包含 **39 个条目**的可靠性检查清单（reliability checklist），每一条都配有一个可以从 diff 中识别出来的触发条件、一项具体检查，以及背后对应的历史线上事故或 PR。其中一条是：`--resume 能正常加载旧版会话记录`。每当会话存储格式或消息类型发生改动，我们就会检查新增字段是否能安全加载——因为老版本的历史记录里并没有这个字段。

Claude 会先读 diff，**只检查触发条件匹配上的那几条（通常是 3 到 10 条）**，这样谁都不需要靠死记硬背去防历史事故重演。

### 一个审查者，多轮递进（而非堆砌多个审查者）

我们不会试图通过在主审查者上面再叠一个更昂贵的第二审查者来提升审查质量——那样做往往还不如专心把主审查者调教好。相反，我们维护一份 `REVIEW.md`，明确告诉审查者针对这块代码应该重点盯什么。

我们也认为审查与验证的每一轮都应当建立在上一轮的基础之上：每一轮都会指向前几轮的上下文和过往失败点，而不是每次都从零把所有东西重查一遍。这样既省钱，又能抓出更多真问题。

### 改动绝对不能修改「审判它自己的检查规则」

如果一笔代码改动能够顺手修改用来评判它自己的检查规则，那这道检查就形同虚设了。因此，我们的 Code Review 永远从**基准分支或默认分支（base / default branch）**读取 `REVIEW.md`，绝不读取当前 PR 分支里的改动。Claude Code 团队确保所有门禁规则都存放在待审改动无法触碰的分支上。

同时，Claude Code 团队只针对**具体提交（commit）**做审查。如果审查还在跑的时候有人又往分支推了新提交，那刚才的审查结果就作废了——在一笔已经过期的 commit 上拿到「审查通过」没有任何意义。

团队还会坚持**先跑便宜的检查**。如果 Agent 还没在本地跑测试就直接 push，它就白白浪费了公共的审查与 CI 资源，去抓一个本该在本地自己抓出来的 Bug。在我们团队，Claude 在发起 PR 前必须先跑完测试、构建（build）和 Linter。你可以通过在 Claude 结束时自动跑测试的 Hook，或者设定「测试全绿」的 `/goal` 来强制执行这一点。

### 新门禁先开「观察模式（Observe Mode）」灰度

在我们自己的仓库里，每一笔 commit 都会被打上印记（stamp），记录它是通过什么方式验证的——甚至包括 `"none"`（未验证），方便我们随时查询哪些提交跳过了验证。

我们还做了一道提交门禁（commit gate）：如果当前会话没有跑过 `/code-review` 或 `/verify`，门禁就可以拦截提交。我们为它设计了三档模式：**关闭（off）、观察（observe）、强制（enforce）**。

- **观察模式（Observe mode）**只记录「哪些提交原本会被拦截」，方便我们先复盘误报（false positives），确保不会误伤正常开发节奏。
- **强制模式（Enforce mode）**则会真正阻断提交。当然，任何提交都可以在 commit message 里写明未做验证的合理原因；如果在同一次会话里提交已经被连续拦截了两次，第三次就会放行，避免把 Claude 彻底卡死——毕竟 Claude Code 也不是十全十美的。

### 在真正要紧的历史真 Bug 上评测你的检查器

Claude Code 团队还会定期**「审查我们的审查者（review the reviewers）」**。我们会追踪：合并后的改动有多少被回滚（reverted）、维护者在合并前打回了多少改动，并抽取一组体量匹配的、合并后一直稳定运行的代码作为干净对照组。

这件事也可以做成一套正式评测（formal evaluation）。在此前的代码审查文章里我们介绍过，Code Review 团队基于历史线上故障和回滚记录搭建了一套评测集：针对每一个历史样本，他们把代码库精确还原到当年审查发生时的状态，并配上一句话标准答案（answer key）写明真正的 Bug 是什么。只有准确描述出该核心 Bug 的审查发现才能得分；同时用合并后长期稳定的改动做对照，防止审查器乱报一气（over-flagging）。调优集（tuning set）与用于最终评估系统的固定测试集严格切分开。

他们还把**原始发现（raw findings）、验证过滤后（post-verification）以及最终发出的审查意见（final review）**这三个阶段的召回率拆开单独评估。这能让他们一眼看清系统是不是在半路上把自己原本已经抓到的真 Bug 给筛丢了——如果只看一个笼统的端到端总分，就完全捕捉不到这层细节。

除了准确性，我们关心的另一个维度是**重要程度**：一个好的审查者能抓出大部分技术上确实存在的问题，但工程师真正关心的是这个问题到底是「必须修（must-fix）」、「建议修（should-fix）」还是「吹毛求疵（nit）」。

我们的 Code Review 正是这样打标签的：**Important（重要）、Nit（细微问题）或 Pre-existing（历史遗留）**。标上 `Pre-existing` 意味着审查者不应该为原本就已经存在的老 Bug 刁难当前 PR 的作者。

最后，Claude Code 团队会把召回率调优到恰到好处的临界点——再往上硬提哪怕一点，就会变成对评测集的过拟合，而不是在真实世界里抓出更多 Bug。

### 把漏网之鱼转化为规则，并定期修剪

在 Claude Code 仓库里，我们有两种方法把漏掉的问题沉淀成新规则：

1. **第一种方法**：从人类审查评论和 PR 回滚记录中提取共性模式。某个问题必须在至少两个 PR 里出现过、且能从 diff 中识别出来，才会被列为候选规则；接着会有三个 Agent 尝试证伪它，最后由人类在 PR 中审核批准。
2. **第二种方法**：拿三个专门找 Bug 的 Agent 去重放某个关联了已知线上故障的历史 PR。如果至少有两个 Agent 抓出了这个 Bug，说明它是可检测的；如果在一个很小的 diff 上居然漏掉了它，这就暴露了一个值得写进 `REVIEW.md` 的规则盲区。

偶发抖动的测试（Flaky tests）也享受同等待遇：**严禁 Claude 跳过它们、严禁随便塞 `sleep` 等待、也严禁无脑重试直到撞大运变绿。** 如果 Claude 实在找不出抖动的根本原因，它必须删掉这条测试，并清清楚楚写下删除原因。

规则同样需要定期大扫除。测试套件、验证步骤和 `.md` 文件如果放任不管只会无限膨胀，所以我们会例行修剪清理，确保留下来的每一条都真正值得运行。

## 好测试，才有好结果

我们最大的体会是：给你的 Agent 一套拥有强反馈闭环的验证手段，会带来天壤之别。请像对待任何核心生产系统一样对待你的验证层——**让它远离待审代码的篡改范围，用真正痛过你的历史 Bug 去给它打分，每当漏掉问题就写下教训确保绝不犯第二次，并定期修剪这些规则让它们始终轻快管用。**

做到这几点，你的工作就会从「逐行苦读每一份 diff」彻底升级为「定义什么叫『做完了』并审查通关证据」——而这，正是让你能同时驾驭几十个 Claude 并行狂奔的真正秘密。
