在构建企业级 AI Agent 的早期阶段，几乎所有工程师都会陷入一种直觉误区：**“模型之所以犯错，是因为我们给它的专用工具还不够细致。”**

于是团队开始陷入无休止的造工具循环：写一个“按部门查报表工具”、写一个“字段校验工具”、写一个“JOIN 关联查询工具”……不知不觉间，单个 Agent 挂载了二三十个高度定制的函数定义。

结果却令人大跌眼镜：工具越加越多，Agent 反而越来越慢、越来越笨。

## 为什么“过度封装”会反噬智能？

当工程团队对线上失败轨迹进行逐条回放拆解时，发现了三个结构性死结：

1. **决策税（Decision Tax）指数级上升**：每次推理前，模型都必须在二十多个命名相近的工具 Schema 之间做阅读理解，消耗大量前置注意力。
2. **人为阉割了模型的原生组合能力**：现代旗舰推理模型在预训练阶段已经阅读过海量 Unix 管道命令（`grep`、`jq`、`awk`、脚本组合），而人为拆碎的窄接口反而堵死了它用一行组合命令直接定位根因的捷径。
3. **文档与实现不同步**：业务表结构一改，二十个专用工具的参数说明就得跟着改，稍微漏改一处就会把模型带进沟里。

## 极简重构：回到「文件系统 + 受控终端」原语

重构方案激进得令人意外——**直接删掉 80% 的专用查询与转换工具，把底层元数据、表字典与业务文档映射为清晰的本地目录树，只给 Agent 留下一把通用钥匙：受控沙箱里的基础文件与命令行原语。**

改造前后的核心指标对比极具冲击力：

- **端到端平均耗时**：从原先多次工具试错的 **77 秒缩短至 28 秒**；
- **复杂长尾问题一次答对率**：从 **80% 跃升至 98% 以上**；
- **平均单次会话 Token 消耗**：下降近 **40%**。

## 结合我们实战的两步落地建议

不要盲目照搬“全盘裸奔开 Bash”，落地到你们自己的产品或内部 Agent 时，建议分两步走：

1. **第一步（把知识变成可 `grep` 的干净目录）**：检查你们喂给 Agent 的背景资料——与其做一套复杂的黑盒向量召回，不如先把文档整理成命名规范、带清晰目录索引的 Markdown 树，让模型能像资深工程师一样按图索骥。
2. **第二步（只对“高危写操作”保留窄接口）**：读操作全面拥抱通用文件与轻量 CLI 原语；只有涉及真实扣款、发外部邮件、改生产数据库等不可逆动作时，才单独封装带权限审批的强类型窄工具。
