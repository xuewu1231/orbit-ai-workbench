## 00:17 开场

再说一次，我叫 Potato。

我在 SpaceXSI 做 Grok Bot。

大家先举个手：有没有人看过别人写的代码，心里想：「这完全是胡说八道。」嗯，我也一样。

但今天，我要说服你们，这些垃圾可以变成金子。

上个月，我做了一件疯狂的事：我往生产环境发了 3000 个 PR（合并请求）。在 agent 出现之前，我们从来不用担心数量的问题，除非是极特殊的情况。

在我上一家公司，他们把这样的人叫做「编码机器」。比如 Bret Taylor，他曾经用一个周末重写了整个 Google Maps。就是那种效率高得不可思议的工程师。

而现在，多亏了 agent，每个人都能成为「编码机器」。我的论点是：软件工程师的工作、编程的目标，就是想办法在大幅提高生产力的同时，保持甚至提升代码的质量。

为了做到这一点，有人把它叫做「软件工厂」。但我更愿意简化一点，我相信一切归结为**信任**。

不是盲目信任，而是往 agent 的环境里投资，让你确信它们会把每件事都做对。

这需要很多努力，我花了半年时间，才做到能发出成千上万个合并请求，其中很多还是在我睡觉的时候发出去的。但这是完全可能的，而且你们花的时间会比我少得多。

那么，先从如何从低信任走向高信任讲起。

## 02:03 信任金字塔

这个倒金字塔展示了我如何给 agent 的环境分配时间。

头两层是确定性的，也就是说，它们基于你自己的代码。

比如，好的 API 设计、架构、重构，或者使用 lint（代码检查工具）、类型系统、编译器，以及各种类型的测试。

你可以把这两层结合起来用，限制 agent 的行动，迫使它们默认就把每件事都做对。

验证——运行时验证和形式化验证——是发现错误、检查系统应该遵守的属性和不变量、以及检查 agent 是否理解了你的目标和意图的好工具。

最后，你要加一些描述性的指令，也就是 rules、skills、`agents.md` 文件——任何需要判断力的东西。

但先从你的代码库讲起。agent 是根据输入数据生成结果的，所以输入的质量真的很重要，而你的代码库就是其中最大的来源之一。

所以，当你修 agent 的时候，考虑把它变成一个确定性检查，而不是在 rules 或者 `agents.md` 里再加一行，因为这样在代码里更容易复现，也更让人信任。

## 03:27 代码库是花园

我喜欢用的一个比喻是，你的代码库就像一座花园。你知道，以前代码是一次几个 PR 一起来的。我记得 2024 年来上班，审阅三个同事写的合并请求。

而今天，这个数字接近 300 个。

所以现在，每个工程师身后都是一个由几百甚至几千个 agent 组成的团队，代码来得如此之快，几乎像一股连续的水流，几乎感觉是有机的，像个活物。

在这个比喻里，你的代码库、你施加的约束、你设置的安全措施，就是新代码在 agent 手下生长时周围的混凝土基础，就像这张照片里的建筑一样。

所以在很多方面，软件工程师的工作变得跟园艺很像。

因为代码是 agent 最大的输入来源，这意味着任何变通写法、反模式、过时代码或者技术债，都很可能被下一个 agent 复制，因为在你的代码库里，它们看起来就像既定的模式。

这就像花园里的杂草或者害虫，不知不觉间，它们就到处蔓延了。

所以，你要让你的代码库尽可能干净，这样 agent 复制到的永远只有高质量的东西。

## 04:57 Dune 框架

好，来看真实的例子。Dune 是我们为 Grok Bot 打造的一个客户端框架，用来实现这种有机架构的想法。

从技术上讲，它没什么太复杂的东西。你可以把 Dune 想成 Electron 应用的 Next.js。

但 Dune 有意思的地方在于，它有很多限制和 lint 规则，我们把在构建桌面应用时学到的很多教训都写进了这些规则里。

其中一个教训是：任何需要微妙技巧才能用好的东西，往往都会导致粗心大意。一个经典的例子就是 React 里的 `useEffect`，对吧？它有它的用处，但经常被误用。有人开玩笑说，要用 `useEffect` 得有个博士学位。换句话说，要把它用好，你真的需要考虑到很多细微差别。

agent 特别不擅长用它。

所以，我们的解决办法就是干脆在产品代码里禁掉它，只允许在 Dune API 内部的某些地方使用。

事实上，这个问题现在已经彻底解决了，我们在代码 review 的时候再也不用修它了。

我们用的另一个有意思的模式，是通过目录结构提供上下文。我们在 Cursor 这个 Electron 应用里注意到的一个反模式是，agent 经常把主线程的代码 import 到渲染线程里，导致长时间的任务和延迟。

所以在 Grok Bot 和 Dune 里，我们把它做得非常规范。

我们有两个顶级目录，字面意思就叫 Electron `renderer` 和 Electron `main`，两个目录之间的 import 被我们的依赖图分析器和某些 lint 规则禁止了。

同样，这些都是简单易设的 lint 规则，但这意味着我们在 review 代码的时候少了一件要操心的事。

## 06:56 注释是借口

我注意到的另一件很神奇的事，是 agent 使用 Markdown 的方式。这适用于文档、代码注释、rules 或者 skills，它们把 Markdown 当成一个为自己没把事情做对找理由的地方。

不知道你们有没有遇到过这种情况，但它们会过度关注你做过的一个小修正，把它当成一条永远不能打破的严格规则。

再举一个 Cursor 的例子。agent 特别喜欢用命令式的定时器，比如 `setTimeout`、`requestAnimationFrame`、`requestIdleCallback`。它们把这当成一个快速修复，用来弥合 VS Code 命令式风格和 React 声明式风格之间的架构冲突。

所以我们这个架构选择，实际上大幅降低了客户端和 agent 的性能。

如果你做过 JavaScript 的性能工作，你就知道，当大量定时器被快速创建和销毁时，会导致频繁的垃圾回收，进而造成卡顿和延迟。

但最糟糕的是，agent 在代码里写了一大堆注释，就像你们在这里看到的红色部分，解释为什么这个快速修复是合理的。

不知不觉间，定时器就到处蔓延了，程序的性能也受到了严重影响。

在 Grok Bot，我们吸取了这个教训，决定干脆**禁掉 99% 的注释**，因为它们很快就会过时。

毕竟，人们本来也很少读这些注释。

而且这又给了 agent 一个借口，让它以「这件事很难」为由，不去做正确的事。

嗯，注释最糟糕的一点是，它们不是强制性的。所以一个看起来很好的意图，你知道的，比如「我告诉下一个 agent 别这么做」，永远不会变成你可以信任的东西。

所以在 Grok Bot 和 Dune 里，我们现在有了 lint 规则，能给出清晰、非常有用的报错信息，提示 agent 去修复根本原因、真正的问题，而不是只打个补丁。

我们的总体原则是：**每当我们修 agent 的时候，要么把它变成一个这样的确定性检查，要么想办法通过更好的 API 设计或架构，在代码里彻底消除这类问题。** 如果你经常这么做，你会发现 review 代码的时候需要考虑的事情越来越少。到了某个时候，你会意识到已经没什么可看的了，你可以直接让 agent 自己合并它们的大部分 PR。

## 09:40 验证

好，继续往下说。验证也是让我们 agent 更加自主、让我们对它们的工作更有信心和信任的非常重要的一部分。而我们的代码 review 流程，现在其实已经归结为分析验证产物，也就是视频、截图、图表、形式化验证这样的东西。

最简单的例子是运行时验证，这只是一种比较花哨的说法，意思是：给 agent 自己运行代码的能力，让它使用人类开发者也会用的调试工具，比如 Chrome DevTools 协议。在我们的运行时验证 skills 里，有一个我们叫做「feature map」的东西。这本质上就是一张从用户视角看、你的应用里所有功能的站点地图。也就是说，当你说「左边面板上的那个东西」的时候，agent 不用猜了，它有了一个共享的词汇表。

在这些 skills 里，我们也用自己的 CLI，这样 agent 每次都能复用同一个 CLI 和驱动程序，减少 token 的使用，而且也是可测试的。

最近，我们也开始研究形式化验证。我们现在用 TLA+ 来验证核心用户流程的模型，比如跨设备、跨平台的通知。我们也用 Lean 来证明某些算法。比如，我们自己做了一个虚拟化库，在里面用 Lean 来确保没有闪烁或者抖动的问题。我们整体上还在试验这种方法。

看起来非常有前景，我们已经通过形式化验证发现了很多错误。

当然，这不是万能药，我们把它看作另一个工具，是 agent 环境里的又一层。

## 11:53 验证的黄金时代

这是一个很短的视频，但我们开始研究的另一件事是基于属性的界面测试。我们用了一个叫 Bombadil 的库，它已经帮我们发现了界面上的几个 bug。

如果从更广的角度看，六个月前我看到了 Cindy 发的一条推文，她写道，因为一些小错误混进了代码，她没办法信任自己的 agent。

而事实上，她要开始信任 agent，缺的就是一个验证流程。而现在，六个月后，她说自己每天 70% 的 token 都花在了验证上。我想说，这跟我的观察是一致的——我自己的大部分 token 也花在了验证上。

如果你仔细看她的流程，这些东西没有一样是新的，或者是我们以前没有的独特东西。

这些只是很好的开发工具，只不过以前用起来可能太贵了，因为它们很难理解、很难写、很难维护。

但 agent 大幅降低了这些成本。我们真的正在进入软件测试和验证的黄金时代，因为 agent 让我们能够比以前划算得多地、彻底得多地测试一切。

形式化验证也能帮你更好地理解你的产品应该如何工作，以及 agent 是否真正理解了你的意图和目标。

我在自己的 pstack 插件里做了一个叫 state chart 的新工具，它能帮你从用户的视角可视化状态机。配合我们提供的视频和截图，看起来要容易得多，而且非常方便。

## 13:32 回报

在 Grok Bot 团队，我们的速度正在增长，而且越来越快。

上个月，我们团队往生产环境发布了惊人的 **11,000 个 PR**，这就是一个疯狂的数字。

我们客户端的发布速度也提高了。我们大概每天发布一个新稳定版。

核心开发团队发布的更新也明显更多了。此外，我们还有很多偶尔参与的贡献者，他们并不总是有完整的上下文，但他们也在贡献。

10 月份，我们有大约 227 人至少创建了一个 PR。

所以，看到这种加速，你可能会想：这不会导致混乱吗？你知道，这不会变成一堆垃圾吗？但实际上，**被撤回的合并请求的数量相对减少了，并且稳定在 0.5%**。

但我认为，关于这种发布速度和请求量，最有意思的是，Grok Bot 的性能自上线以来不仅保持稳定，而且在很多方面都有所提升。

所以，启动、打字、打开新的聊天、在它们之间切换——一切都变快了。请注意，Grok Bot 目前仍然是一个 Electron 应用。所以它是有上限的，对吧？但它已经比今天存在的许多其他 agent 界面快得多了。对于一个开发速度这么快、贡献者这么多的 Electron 应用来说，我觉得这已经相当不错了。

## 15:11 先打地基

所以，在你创建一个「软件工厂」、把所有能自动化的东西都自动化之前，先试着通过改进你自己的代码库来微调 agent 的表现。先从 lint 规则开始，防止新的反模式出现，然后再清理代码里旧的反模式。还要确保你的验证策略真正可靠。

无论如何，这些工作中的大部分本来就是自动化的前提条件。如果你的内部写代码循环产出的是垃圾，那么自动化这个循环只会产出更多的垃圾，你还得花越来越多的 token 来修复问题，而我们知道，那是非常昂贵的。

当你在代码库、静态分析以及运行时验证上做了这些投入之后，你会发现，有了这样的基础，很多事情都变得可能，你可以很轻松地在上面搭建自己的工厂。

当你准备好了，Grok Bot 就是搭建那个外环的一个很好的方式。我们有各种各样的连接器和例程，可以运行 Cursor、云端 agent，以及让你管理几百甚至几千个 agent 的项目。举一个快速的例子，你知道，每次我们发布一个新版本，Grok Bot 就会自动为我们在 Cursor 里启动一个新项目，对整个应用、整个构建做 fuzz（模糊测试），通过运行这个应用、像真实用户一样使用它来发现 bug。

然后，它会针对发现的每个 bug 打开一个带修复的 PR，并自动合并它们——听起来可能很疯狂。之所以能这样，是因为我们的代码库质量足够高，PR 默认就是成功的，我们部署的大部分产品代码不再需要深入的人工 review。

所以，当你有了坚实的基础和良好的有机架构，你就可以把混乱变成金子，以很高的速度发布产品，同时不牺牲质量。

我叫 Potato，也就是 Lauren。再次感谢大家听我的分享。

:::guide 助读总结 · 从这场演讲带走的 4 条工程铁律
1. **修 Agent 先修代码库，别只往 `AGENTS.md` 里塞规则**：现有的技术债会被下一个 Agent 当成标准模板照抄蔓延。
2. **用 Lint 报错信息教 Agent 改根因**：凡是需要微操才不会踩坑的 API（如裸写 `useEffect` 或跨进程乱引模块），直接用架构与 Lint 物理封死，并在报错文本里告诉 Agent 正确写法。
3. **警惕「解释性长注释」**：Agent 常把写长篇注释当成逃避真正修复架构冲突的借口。
4. **把 70% 的 Token 投资在验证产物上**：通过 Feature Map + Chrome DevTools / 属性测试让 Agent 自己跑出截图、录屏与状态证明，人类只审证据。
:::
